## Phase 5: 分层记忆系统 V1

### 概述

构建基于向量数据库的分层记忆系统，实现角色的长期记忆能力。

### 技术实现

- **记忆管理器**: [vdb_tools/hierarchical_memory_db.py](file:///d:/Data/PYC/LLMRolePlay/project_version_3.2.6_workspace/vdb_tools/hierarchical_memory_db.py) 中的 `HierarchicalMemoryManager` 类

## Phase 9: 记忆系统升级 - 多级总结

### 概述

将记忆系统从单级日级总结扩展为四级分层架构，支持递进式记忆压缩。

### 技术实现

- **周级总结**: `compress_to_weekly` 方法，将日级总结压缩为周级总结
- **月级总结**: `compress_to_monthly` 方法，将周级总结压缩为月级总结
- **年级总结**: `compress_to_yearly` 方法，将月级总结压缩为年级总结
- **递进式压缩逻辑**: 日→周→月→年的层级递进，每层使用上一层的结果
- **保留策略**:
  - L1 日级: 保留 14 天
  - L2 周级: 保留 8 周
  - L3 月级: 保留 12 个月
  - L4 年级: 保留 100 年
- **时间分区**: ChromaDB 按周（W14）、月（202603）、年（2026）分区存储

### 新增目录结构

- `summary_L2_weekly/` 周级总结向量库
- `summary_L3_monthly/` 月级总结向量库
- `summary_L4_yearly/` 年级总结向量库

## Phase 11: 深度回忆功能

### 概述

实现系统的核心特色功能——深度回忆，让角色能够真正"记住"过去的对话。

### 技术实现

- **三种回忆模式**:
  - `off`: 不进行深度回忆，仅使用短期记忆
  - `normal`: 从分层总结库（L1-L4）检索记忆
  - `enhanced`: 从最近半年的原始记录库检索
- **时间路由检索**: `retrieve_with_time_routing` 方法，根据时间范围智能选择检索来源
- **原始记录检索**: `retrieve_from_raw_records` 从 ChromaDB 原始记录中检索
- **自动意图检测**: 检测用户输入中的回忆关键词（"你还记得...吗"、"仔细回忆"、"很久以前"等）
- **结果去重**: 多源检索结果的合并与去重处理
- **时间标签标注**: 检索结果标注时间标签（如 [数日前的模糊回忆]）

### 新增功能

- 回忆模式状态管理（按角色保存）
- 回忆按钮循环切换（关→正常→增强→关）
- 自动意图检测关键词列表

## Phase 12: LLM 智能总结

### 概述

引入基于大语言模型的智能总结算法，替代原有的非 LLM 总结方式。

### 技术实现

- **总结模型**: 使用 Qwen3.5-Flash，开启思考模式（enable_think=True）
- **思考预算**: thinking_budget=4096 tokens
- **四层专用 Prompt 模板**:
  - 日级: 突出重要事件和情感变化（200-400 字）
  - 周级: 提炼核心主题和重要发展（300-500 字）
  - 月级: 提炼核心事件和成长变化（400-600 字）
  - 年级: 提炼核心主题和重大变化（500-800 字）
- **回退算法**: LLM 总结失败时自动降级为关键词提取算法
- **优先级**: LLM 总结优先，非 LLM 算法作为兜底保障

### 新增/修改模块

- `vdb_tools/hierarchical_memory_db.py` 中的 LLM 总结逻辑
- 四层 Prompt 模板

## Phase 22: 前端代码模块化重构

### 概述

将前端核心文件 `chat.js` 从 3222 行单文件（100+ 函数、13 个功能域）拆分为 12 个职责单一的模块文件加 1 个入口文件，放置于 `app/static/js/modules/` 目录下。同时修复拆分过程中遗漏的变量声明和事件绑定问题。本次重构为后续功能迭代奠定可维护的代码基础。

### 动机

随着知识库引用系统（Phase 21）、文档选择器等复杂功能的持续迭代，`chat.js` 已膨胀至 3222 行，涵盖角色管理、聊天核心、WebSocket、输入气泡、图片裁剪、模型选择、统计页面、知识库 CRUD、文档选择器/引用 Tag 等 13 个功能域。维护成本急剧上升，修改一处容易影响其他模块，代码审查效率低。

### 技术实现

**拆分方案**

采用「零构建工具」策略：所有函数保持全局作用域（`function` 声明），通过 `<script>` 标签按依赖顺序加载，确保与现有 HTML 内联事件处理器（`onclick=` 等）完全兼容。

**目标架构**

```
app/static/js/
├── app.js                    # 入口文件 (~103行) — 初始化 + 顶层事件监听
└── modules/
    ├── state.js              # 全局状态树 + DOM缓存 + 常量 (~69行)
    ├── utils.js              # 纯工具函数 (~109行)
    ├── websocket.js          # WebSocket 连接管理 (~86行)
    ├── roles.js              # 角色列表 + 对话管理 + 侧边栏 (~585行)
    ├── chat-messages.js      # 消息气泡渲染 + 历史加载 (~113行)
    ├── input-ui.js           # 输入气泡 + 发送 + 功能开关(~283行)
    ├── image-cropper.js      # 图片上传 + Canvas裁剪器 (~274行)
    ├── model.js              # 模型选择器 + 启动序列 (~141行)
    ├── stats.js              # 统计页面 (Chart.js) (~456行)
    ├── knowledge-base.js     # 知识库CRUD + 文档管理 (~461行)
    └── doc-selector.js       # 文档选择器 + 引用Tag + 字符偏移计算 (~530行)
```

**加载顺序**

`state.js`（定义所有共享状态）→ `utils.js` → `websocket.js` → `roles.js` → `chat-messages.js` → `input-ui.js` → `image-cropper.js` → `model.js` → `stats.js` → `knowledge-base.js` → `doc-selector.js` → `app.js`（最后执行事件绑定初始化）

**关键设计决策**

| 决策 | 选择 | 理由 |
|------|------|------|
| 模块化方式 | 多文件 `<script>` 加载 | 兼容现有 HTML 内联事件，无需构建工具 |
| 作用域 | 全局 function 声明 | onclick= 等内联处理器可直接调用 |
| 状态管理 | 集中于 state.js | 单一来源，避免循环依赖 |
| 入口文件 | app.js 仅含初始化 | 最小化入口，职责清晰 |
